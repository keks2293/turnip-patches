# Что из этого следует (и что нет).
# 1. Объём записанной меты у R8 не зависит ни от резерва драйвера, ни от сетки из
#    окружения: 1024 байта при метаплоскости 8 КБ и при 16 КБ (exp-17,
#    results/test-8bpp-grid-sweep.log), 256 байт на образе 256x256. Везде 1 байт
#    на 256 текселей — ровно столько ячеек даёт сетка {32,8}, по которой живёт
#    Y-плоскость NV12, тогда как драйвер под plain-8bpp резервирует и обходит
#    плоскость по {16,4} (вчетверо больше ячеек).
# 2. Первые 4 КБ мета-резерва у рабочего NV12 выглядят так же: четыре куска по
#    256 байт с шагом 1 КБ. Отличие в том, что у NV12 выше занято ещё ~2.5 КБ и
#    значения разные (27, 4, 125, 247…), а у R8 — ровно 1024 байта со значением
#    0x1f и больше ничего.
# 3. Это свидетельство про объём, а не про адрес: часть резерва меты —
#    выравнивающий зазор, где может лежать мусор от предыдущего владельца BO,
#    поэтому «читатель натыкается на нетронутые байты и трактует их как
#    сжатый в clear colour блок» остаётся гипотезой, а не выводом из дампа.
# 4. Форма записанных кусков (четыре куска по 256 байт с шагом 1 КБ) не
#    описывается ни одной из разбираемых сеток; чем именно железо выбирает
#    геометрию для FMT6_8_UNORM, дамп не говорит. Перебор сетки из окружения
#    (exp-17) это не проверяет: с blockheight >= 8 GPU падает, а с
#    blockheight <= 4 меняется только размер резерва, портится ровно то же.
# 5. Побайтово совпадающие плоскости данных у AA и AB означают только равенство
#    содержимого (оба писателя заливают один и тот же узор). Вывод про то, что
#    2D-копир не пишет мету, держится на нулевой мете и нулевом чтении пробы AB
#    с LINEAR-контролем, а не на дампе.
